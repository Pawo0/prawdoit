## 0. Summary

1. **Infrastructure.** Sound for a one-user hackathon demo, and the verification core is well separated from the
   channels (every channel calls `service.run_check`). It is **one process holding everything**: two models, the
   index, the job registry, the rate limiter, caches, the demo outbox and the source scheduler. It does not survive
   a second replica, and under concurrent load nothing limits CPU-bound inference on the synchronous endpoints.
   `docs/COSTS.md` calls the API "stateless"; the code is not.
2. **Two-tier idea.** The system already has two tiers (`/api/quick` and `/api/check`). The proposal as worded — a
   fast model that tags content as "suspicious / possibly false" — should **not** be built. No evidence-free signal
   separates false from true text, and my offline numbers show the two available cheap signals do not discriminate.
   A visible "suspicious" tag without a source also conflicts with the task rules. A **reduced version is worth
   building**: tier 1 as a *router* with three states (`none` / `candidate` / `match`), where only `match` is
   visible and always carries a named source, and `candidate` is invisible and only decides what tier 2 checks.
3. **Tier 2.** The limiter is not retrieval depth or NLI strength. In the stored blind-set results, 6 of the 9
   remaining misses have the correct fact-check as the top source and still abstain. The cheap wins are data and
   matching: 750 of 3,083 indexed fact-check claims have no mapped verdict, claim extraction caps at 3 sentences,
   and the "opinion" rule fires before retrieval.
4. **Containers.** Ship one image and one compose file now (proposed below, compose syntax validated, image never
   built). The properly split topology needs eight code changes, listed in §4.4.

## 1. What the task statement constrains

Requirements that the proposals below must respect (section of the PDF in brackets):

- A verdict may not rest on domain, author, channel, popularity, share count **or a label generated by the same
  model** [5, "Ograniczenia i zakazy"]. A catalogue match may trigger a neutral warning in explicitly defined cases,
  never a verdict [3, scenario I].
- Every factual statement presented as a finding must lead to a source: title, publisher, date, link, fragment [2, 5].
- The system "is not to play the role of an automatic judge of truth"; it should encourage the user to read the
  evidence [9].
- Abstain when evidence is insufficient; failure, unclear question and out-of-scope are not verdicts [2, 5].
- An LLM output may not be presented as fact without a verifiable source basis [5].
- Conflicting sources must be shown as a divergence, without arbitrary certainty [6, scenario C].
- Privacy: minimisation, masking, defined retention, session deletion [5]. Transparent information on where data is
  processed and limited non-EEA dependencies are rewarded [3].
- Instructions found in analysed material must not change behaviour; the event is logged [2, scenario E].
- Median ≤ 30 s for text/URL; cost of 100 tests reported [6].
- Web and second channel must give the same substantive result for the same query and conditions [5, scenario G].
- Information loop: no false message about forwarding a case; one case per repeated question [6, scenario H].
- The prototype must be runnable by the jury from the team's instructions; a Docker container is optional [4, 5].
- Scoring: verification quality 30 %, security/transparency 20 %, deployment potential 20 %, usability 15 %,
  innovation 15 %. Bonus features count only if the basic requirements are met [8].

## 2. Is the current infrastructure sound?

### 2.1 How requests flow

**Web.** `checkAsync` in `web/static/app.js` posts to `POST /api/check/async` and polls `GET /api/jobs/{id}` every
700 ms; `checkWithProgress` falls back to synchronous `POST /api/check` on 404/405/501. (No line numbers: the
file was being edited by someone else while I read it.) The job runs `service.run_check`
in a 2-thread pool (`jobs.py:32`) and reports stages through a callback (`jobs.py:72-76`).

**Extension (after the teammate's change).**
- Manual path, now the primary entry: floating "Sprawdź" button → element picker (`content.js:276-313`) →
  `checkText` (`content.js:366-423`) → background → **synchronous** `POST /api/check` with `channel:"extension"`,
  text ≤ 6,000 chars, 45 s abort (`background.js:27-33, 54-60`). A parallel `/api/quick` call annotates the picked
  element (`content.js:373-375`).
- Automatic path: only on 34 listed hosts plus localhost, only after the first-run notice is accepted
  (`content.js:56-57, 254`). Visible items (IntersectionObserver, 20 % visible, `content.js:221-223`) are batched,
  ≤ 16 items, each ≤ 1,500 chars, first flush after 500 ms and then every 300 ms (`content.js:227-241`) →
  `POST /api/quick` with `page_url: null` (`background.js:44`).
- Rendering: `wysokie` → overlay covering the item when mode is `zaslon`, the default (`content.js:209-217`,
  `background.js:5`); `srednie` → badge "! Sprawdź tę treść".

**Chat channels.** WhatsApp/Messenger webhooks verify the signature, acknowledge and process in a FastAPI
background task (`channels/meta.py:102-110, 146-154`); `?demo=1` runs synchronously and returns the reply.
The Discord bot and the MCP server are separate processes that call `POST /api/chat-reply` / `POST /api/check`
over HTTP (`bots/discord_bot.py:32`, `bots/mcp_server.py:36`). PWA share target: `api.py:224-232`.

**Inside `run_check`** (`service.py:74-240`): optional URL fetch with SSRF guard → injection scan → ≤ 3 claims
(`service.py:150`) → Google Fact Check started in parallel if a key is set → `engine.verify_claim` per claim →
live search on trusted domains when the corpus gave nothing (15 s budget, `websearch.py:67-73`) → optional LLM
rewording → moderator case → short answer → audit row in SQLite.

**`/api/quick`** (`service.py:276-337`): per item up to 8 sentences plus the first 400 chars (`service.py:269-273`)
→ one batched embedding → nearest claim among those rated false/misleading/mixed (`index.py:285-293`) → NLI for
everything with cosine ≥ 0.74 (`service.py:303-313`) → `engine.same_claim` → risk → level. No audit row, no
security scan, no rate limit.

### 2.3 What runs in the API process

One `uvicorn` process (`[local]`: a single process, no `--workers`). It holds: the embedder
(`sdadas/mmlw-retrieval-e5-small`) and the NLI model (mDeBERTa-v3-base), both loaded as fp32 on CPU
(`index.py:78`, `nli.py:44`); the whole index; the 2-thread job pool; the source scheduler as a daemon thread
(`admin_api.py:59-62`, `scheduler.py:233-261`), which also starts `ingest/*.py` as subprocesses for 17 of the 53
registry entries (`fetchers.py:643-655`); the static web UI (`api.py:185-221`).

Memory: 117.65 M parameters for the embedder and 278.8 M for the NLI model `[card]`, so about 0.47 GB + 1.1 GB of
weights in fp32, roughly 2–2.5 GB resident when hot `[est]`. On the dev machine the process showed 419 MB RSS with
9 GB of swap in use `[local]`, so most of it was paged out.

### 2.6 Before a live jury demo

1. Set `PRAWDOWID_RATE_LIMIT` high (e.g. 300) or run without a proxy in front.
2. Set `PRAWDOWID_SCHEDULER=0` for the session; refresh sources beforehand.
3. Set real `PRAWDOWID_ADMIN_TOKEN` / `PRAWDOWID_MODERATOR_TOKEN` if the URL is public.
4. Send one warm-up check right before presenting. The first case of each stored eval run took 4.5 s, 18.2 s and
   13.4 s against a median of 0.58 s `[M-team: eval/results_2026-11-21*/results.md]`; the cause (cold caches,
   paging) is my inference.
5. Keep automatic scanning off in the presenter's browser unless it is the thing being shown.
6. The extension's default API address is `http://localhost:8000` (`background.js:5`); a jury member installing it
   against a remote server must change it in the popup.
7. If a `cloudflared` tunnel is used, say so in the data-processing note: traffic passes through a non-EEA provider.

## 3. Two-model split for the extension

### 3.1 What the current quick path can and cannot detect

It answers one question: *does this text repeat a claim that a fact-checker in our corpus already rated false,
misleading or mixed?* It can detect that when the wording is close.

It structurally misses:

| Case | Why |
|---|---|
| A false claim nobody in the corpus has checked | nothing to match; 2,148 eligible claims `[M-me]` |
| A fact-check whose verdict was not mapped | 750 of 3,083 indexed claims have `verdict: null` — all 290 Konkret24, 313 FakeNews.pl, 60 Pravda, 56 Demagog, 31 CheckFirst `[M-me]`; they can never produce a tag or a verdict |
| Claims contradicted by official data (numbers, dates, legal acts) | the numeric and legal checks exist only in `engine.verify_claim` |
| Paraphrases | a tag needs cosine ≥ 0.80 with entailment ≥ 0.8 and lexical overlap ≥ 0.4, or ≥ 0.86 (`engine.py:356-360`) |
| True but outdated or out-of-context content (scenario B) | no date or context logic in the quick path |
| Conflicting fact-checks (scenario C) | true-rated claims are not searched |
| Polish posts matching English entries | 300 of the 2,148 eligible claims are English (EUvsDisinfo) `[M-me]`; the embedder is a Polish retrieval model — cross-lingual reach not measured |
| Text in images and video | no OCR |
| Sentences beyond the 8th, text beyond 2,000 chars | `service.py:269-273` |
| Items under 40 chars, paragraphs under 60 | `content.js:39, 256` |
| Sites outside the 34-host list | `content.js:56-57` |

### 3.2 Offline measurements that bear on the idea `[M-me]`

**A. Check-worthiness heuristic** (`claim_kind == "fakt"` and `checkworthiness ≥ T`, the functions tier 2 uses):

| Text | n | T ≥ 0.2 | T ≥ 0.4 |
|---|---|---|---|
| Demagog claims rated false / misleading / mixed | 1,173 | 96.6 % | 62.7 % |
| Demagog claims rated true | 65 | 95.4 % | 86.2 % |
| Sentences (40–400 chars) from MSZ news on gov.pl | 4,369 | 95.7 % | 63.3 % |
| Sentences from MON news | 503 | — | 63.2 % |
| Eval inputs expected false/misleading (three sets, any sentence) | 64 | — | 75 % (48/64) |

The heuristic tags debunked claims and ordinary ministry sentences at the same rate. It measures "is this a
factual sentence", which is what it was written for. It carries no information about falsity.

**B. Cosine to the nearest debunked claim** (cached claim embeddings, self-match excluded):

| From | n | median | ≥ 0.74 | ≥ 0.80 | ≥ 0.86 | ≥ 0.88 |
|---|---|---|---|---|---|---|
| Claims rated **true** → nearest debunked claim | 128 | 0.794 | 94.5 % | 43.0 % | 3.1 % | 2.3 % |
| Debunked claim → nearest other debunked claim | 2,148 | 0.807 | 93.0 % | 55.0 % | 16.9 % | 9.1 % |
| Debunked claim → nearest debunked claim of another publisher | 2,148 | 0.784 | 82.9 % | 35.6 % | 6.5 % | 3.7 % |

Consequences:
- Between 0.74 and 0.86 cosine does not separate true from debunked claims; only above 0.86 is it selective.
  Similarity alone cannot be a tagger.
- The quick path's NLI gate at 0.74 passes almost everything topical. Moving the gate to 0.80 changes no output
  (see problem 2) and, on this sample, removes more than half of the NLI calls (94.5 % → 43.0 %).
- Two of the four true/debunked pairs above 0.86 are real hazards: the Pravda/Demagog pair quoted in §2.5
  (0.900), and "Rosjanie zabili w Buczy ponad 400 osób" (true, Pravda) against "Rosyjskie zbrodnie wojenne w
  Buczy zostały zainscenizowane" (false, FakeNews.pl) at 0.879. Whether NLI rejects them was not run.

**C. Tier 2 on the stored eval sets** `[M-team: eval/results*/results.json]`:

| Run | macro-F1 | false/misleading cases matched | abstained | other |
|---|---|---|---|---|
| Blind set 2, first run | 0.747 | 11 / 19 | 6 | 2 |
| Blind set 2, after fixes | 0.901 | 14 / 19 | 5 | 0 |
| Held-out, after fixes | 0.937 | 17 / 20 | 3 | 0 |

Latency with live search off: median 0.56–0.58 s, p95 1.7–2.0 s. With live search 6–15 s
`[M-team: docs/COSTS.md]`. These sets were written from the corpus, so they measure paraphrase robustness on
*known* claims and say nothing about novel ones. After the fixes they are no longer blind.

### 3.4 The central tension

A tagger must not miss, and a visible "suspicious" mark on true content is harmful. Both hold only if the two
properties are assigned to **different outputs**:

| State | Meaning | Recall / precision target | What the user sees |
|---|---|---|---|
| `none` | not a checkable factual sentence | — | nothing |
| `candidate` | a factual sentence that tier 2 could check | **recall**: ≥ 95 % of items for which tier 2 returns false/misleading | **nothing**. Optional neutral affordance on hover or in a "show checkable" mode: magnifier icon, label "Sprawdź". No colour, no warning word. |
| `match` | text repeats a claim rated by a named fact-checker | **precision**: ≤ 1 % of true items tagged | sourced notice (below) |
| `verified` | tier 2 finished with a decisive verdict and ≥ 1 cited fragment | tier-2 quality | sourced result |

Rules that follow from §1:

1. **A tag is never a statement about truth without a source.** No "podejrzane", no percentage, no colour scale.
   The teammate's card already follows this.
2. **`match` wording** (keep the current text): "Podobną informację {wydawca} ocenił(a) jako {ocena} ({data}).
   To dopasowanie treści, a nie pełna weryfikacja." plus the link and "Sprawdź szczegóły".
3. **`verified` wording** in automatic mode, only for `falszywe` / `wprowadzajace_w_blad` / conflicting sources:
   "Źródła przeczą tej informacji: {wydawca}, {data} →". `brak_dowodow`, `nie_podlega_weryfikacji` and
   technical errors render **nothing** in automatic mode; they are shown only when the user asked.
4. **Conflict suppresses the tag.** If a true-rated claim is as close as the debunked one (within 0.03 cosine),
   show "Źródła podają różne informacje" or nothing. Today the quick path cannot see this.
5. **Badge by default, overlay opt-in.** Covering content on an automated similarity match is the strongest
   intervention available and sits closest to "automatic judge". The setting exists (`mode`); the default is
   `zaslon` (`background.js:5`).
6. **The tag never feeds the verdict.** Tier 2 must return the same result whether it was reached through a tag
   or typed into the web page. Tier-1 output is routing only.

What thresholds mean, in words the methodology page can use:
- gate threshold: "below this we do not look at the sentence at all" — tuned for recall;
- match threshold: "at or above this we show a fact-checker's rating next to the text" — tuned so that at most
  1 in 100 true items is marked, measured on true-rated fact-check claims and on official-source sentences.

### 3.5 Hand-over from tier 1 to tier 2

```
browser                               server
visible item ─► regex gate ─► dedup by hash ─► POST /api/v1/tag (batch ≤ 16)
                                               embed → cosine to rated claims
                                               cos ≥ 0.80 → NLI → same_claim → match | candidate | none
                 ◄──────────── states + priority + auto-check budget ──────────
match      → badge with source now; full check on click
candidate  → top-N by priority → POST /api/v1/verify {mode:"auto"} → poll → badge only if decisive
click      → POST /api/v1/verify {mode:"manual"} → poll → result window (any outcome)
```

- **Automatic tier 2**: at most **3 items per page view**, chosen by priority = near-miss similarity (cosine
  0.74–0.80 to a debunked claim) > high-risk topic (`engine.HIGH_RISK`) > check-worthiness score > style cues.
  Everything else waits for a click.
- **Automatic mode restrictions**, all following from §1:
  - `live_search: false`. Live search sends claim keywords to third-party site searches and, with a key, the
    claim text to Google (USA) (`websearch.py:593-595`). That is acceptable for an explicit user request and not
    for passive browsing.
  - no moderator case (`service.py:208-220` would otherwise fill the analyst queue from people's feeds);
  - audit row without the text: hash, channel `extension-auto`, sources, verdict, timings; short retention.
  - A manual check of the same item reruns with live search and supersedes the automatic badge, because the
    conditions differ.
- **Caching**: key = SHA-256 of whitespace-normalised text. Client: `Map` per page (exists, `content.js:170`),
  plus `storage.session` across tabs. Server: tier-1 results (exists, 5,000 entries) and tier-2 results for
  automatic mode, TTL until the next index reload.
- **Batching**: keep ≤ 16 items per request, but send the next batch only when the previous one returned.
  Today batches overlap every 300 ms regardless of server speed.
- **Deduplication**: the same hash in flight is not sent twice; `idempotency_key` on verify.
- **Rate limits**: tag — 60 batches/min per client; automatic verify — 20/min per client and a global concurrency
  of 1; manual verify — as today. On 429 the extension stops scanning for `Retry-After`; it never renders a tag
  for an error.
- **Budget**: tag p95 ≤ 1.5 s per batch; automatic verify ≤ 3 s per item with the local corpus; manual ≤ 30 s
  (task limit). CPU: one tag batch ≈ 0.2–1 CPU-s `[est]`, one local check ≈ 1–2 CPU-s `[M-team: COSTS.md]`.
  A 4-vCPU server therefore carries tens of simultaneously scrolling users, not hundreds `[est]`; beyond that
  tier 1 has to move into the browser (option C).

### 3.6 What "tier 2 works better and does not miss cases" requires

"Not miss" cannot mean a verdict for everything: for a claim outside the corpus and outside the trusted sites
the correct output is abstention. It can mean two things: no checkable sentence is silently dropped, and a claim
that *is* in the sources is matched. Current limits, in order of payoff:

1. **Unmapped verdicts (data).** 750 of 3,083 fact-check claims have no verdict `[M-me]`. Blind case B2-07
   ("przymusowy pobór kobiet") retrieved the right Konkret24 article and abstained because that article has no
   rating. Fixing the harvesters' rating extraction is the largest recall gain available and needs no model.
2. **Claim extraction drops sentences.** For inputs over 2 sentences or 400 chars only factual sentences scoring
   ≥ 0.4 are kept, at most 3 (`claims.py:50-53`, `service.py:150`). 37 % of Demagog's debunked claims fail that
   filter as standalone sentences `[M-me]`; such a sentence is dropped whenever another sentence in the same text
   passes. A URL input of 6,000 chars is reduced to 3 sentences. Fix: embed every
   sentence (one batch), keep any sentence with a rated claim at cosine ≥ 0.74 in addition to the top 3, and
   return the list of sentences that were not checked.
3. **The opinion rule runs before retrieval** (`engine.py:368-377`). A false factual claim wrapped in evaluative
   words ("Skandal…", "absurd", "powinien") is returned as "not verifiable" without a lookup; blind case B2-05
   failed this way in the first run. Fix: do the claim match first and skip R1 when a rated claim is close.
4. **The same-claim decision.** In 6 of the 9 remaining misses (B2-04, B2-07, B2-11, B2-12, H29, H51) the correct
   fact-check is the top source and the result is still "brak dowodów" `[M-team: results.json]`. Retrieval found
   it; the cosine + entailment + lexical-overlap rule rejected it. Options:
   - **More keys per fact-check** (no new model): index the title and the first sentence next to the `claim`
     field (`index.py:250-254` uses one text per document). Titles such as "Czy na Ukrainie trwa przymusowy pobór
     kobiet" are often closer to how people phrase the rumour.
   - **Cross-encoder reranker** on the top 10 candidates: `sdadas/polish-reranker-base-ranknet`, Apache-2.0,
     124 M parameters, 498 MB `[card]`. It scores relevance, not polarity, so NLI stays for negation. It adds
     about 0.5 GB RAM and 0.3–0.6 s per claim `[est]`, and its threshold must be calibrated on `cases.jsonl` and
     checked on the other two sets. Worth doing after the deadline; a regression risk today.
   - **LLM for query reformulation or decomposition**: rewrite a noisy post into 1–3 declarative claims and use
     them **only as additional retrieval queries**; stance and rules are still evaluated against the user's
     original sentence and the verbatim source fragment. That keeps the LLM out of the fact path and matches the
     task's allowed uses ("rozumienie pytania, wyszukiwanie i porównywanie materiałów"). Validate the output like
     `llm.simplify` does (no new numbers or names), neutralise the input first (`security.neutralize`), give the
     model no tools. Cost: seconds per claim on CPU with a local 1.5 B model `[est from M-team]`, or an EU-hosted
     API that must be disclosed.
5. **Where a stronger model would not help.** A larger NLI model: numbers and dates already go through
   deterministic rules, and the misses above are matching failures. A deeper retriever: the right document is
   already retrieved. An LLM that judges truth: forbidden.
6. **Speed that buys recall.** The NLI repo ships a quantised ONNX file (339 MB against 558 MB safetensors)
   `[card]`. `docs/COSTS.md` expects about 3× on CPU (unverified). Scores shift under quantisation, so the
   thresholds (`config.py:43-44`) need re-validation.
7. **Safety of the match rule.** `same_claim` returns True at cosine ≥ 0.88 with no entailment requirement
   (`engine.py:357`). 2.3 % of true-rated claims have a debunked neighbour that close `[M-me]`. Require either
   entailment ≥ 0.5 there too, or the absence of an equally close true-rated claim.

### 3.8 Measuring the tagger with data in the repo

| Set | Source | n | Used for |
|---|---|---|---|
| P-para | `eval/cases*.jsonl`, text cases whose expected verdict is only false/misleading | 64 `[M-me]` | recall on paraphrases of known claims |
| P-loo | Demagog claims rated false/misleading/mixed, with their own document removed from the index | 1,173 | how often another fact-checker's entry still catches the claim |
| N-true | fact-check claims rated true (Demagog 65, Pravda 49, FakeNews.pl 12, other 2) | 128 | hard negatives: topically close to debunks |
| N-official | sentences from `official_govpl_msz.jsonl`, `mon_aktualnosci.jsonl`, `kprm_wydarzenia.jsonl` | ≈ 5,800 | ordinary true content |
| N-other | eval cases expected confirmed, no-evidence (D) and opinion (O) | ≈ 60 | must not show a visible tag |

Metrics, each with a Wilson 95 % interval:
- `recall_candidate` = share of P items with state ≥ candidate. Target ≥ 0.95.
- `recall_match` = share of P items with state = match. Report; no hard target.
- **tier-2-relative recall** = among all items for which `/api/check` returns false/misleading, the share tier 1
  did not drop. This is the number that answers "does the tagger make us miss cases".
- `false_tag_rate` = share of N items with state = match. Target ≤ 1 % on N-official, ≤ 3 % on N-true.
- `pass_rate` = share of N-official forwarded as candidate (cost only).
- latency per batch of 16, p50 and p95.

Caveats: 64 positives give an interval of roughly ± 7–10 points; tune on `cases.jsonl` and half of N-true, report
on the rest; Demagog ratings are ground truth for the claim as worded by Demagog, not for a paraphrase.

What I could measure without a model is in §3.2. `recall_match` on P-para needs the embedder and was not run.

### 3.9 Recommendation

**Do a reduced version. Do not add a second model.**

Smallest version worth building today, in order:

1. `service.py:303`: gate NLI at 0.80 instead of `claim_match_soft`. Same output, fewer NLI calls.
2. Rate-limit `/api/quick` and send batches sequentially from the extension.
3. Extension manual check through `/api/check/async` + polling (the endpoints exist).
4. Quick path returns `candidate` for the near-miss band and high-risk topics; the extension renders nothing for
   it and sends at most 3 per page to `/api/check/async` with two new request flags (`mode: "auto"`,
   `live_search: false`) that also skip the moderator case. Badge only for a decisive verdict with evidence.
5. Suppress the match when a true-rated claim is equally close.
6. One script that produces the table in §3.8.

Not today: in-browser model, a trained check-worthiness classifier, a reranker, an LLM in the query path.

Main risks of even the reduced version: false tags on true content from the ≥ 0.88 shortcut; analyst queue and
audit log filling from passive browsing if the `auto` flag is forgotten; CPU contention with the manual checks
the jury is watching; DOM adapters breaking on Facebook/X.

## 4. Containerisation and deployability

### 4.1 Service decomposition

| Service | Contains | Why separate / why together |
|---|---|---|
| **gateway** | HTTP API, channel webhooks, admin and moderator API, job API, rate limiting, audit reads | no torch, starts in a second, scales horizontally, the only thing exposed |
| **tagger** (tier 1) | embedder, claim matrix, NLI confirm for cosine ≥ 0.80 | latency-sensitive, many small requests; must not queue behind 15-second checks |
| **verifier** (tier 2) | embedder, NLI, full index, numeric/legal rules, live search | CPU-heavy, bursty, queue-driven; one job at a time per replica with all its cores |
| **ingest** | scheduler, fetchers, `ingest/*.py`, embedding of new documents | singleton, the only writer of corpus and embedding cache, different dependencies, must not steal CPU from serving |
| **db** | Postgres: audit, cases, feedback, source runs, jobs | shared durable state |
| **cache** | Redis/Valkey: queue, tier-1 cache, rate limits, job stages | shared ephemeral state |
| **proxy** | TLS, static `web/`, client IP | — |
| optional | Discord bot (already a separate HTTP client), self-hosted LLM, SearXNG | — |

Stay together: retrieval, NLI and the rules inside tagger/verifier. The index is a 33 MB matrix
(21,560 × 384 × 4 bytes) next to code that reads it thousands of times per request; a separate vector store or
model server would add latency and failure modes for no gain at this corpus size.

### 4.2 State and model weights

- **Weights: bake into the image.** 235 MB + 558 MB plus tokenizers `[card]`. Start is then offline
  (`HF_HUB_OFFLINE=1`) and reproducible for the jury; Hugging Face is no runtime dependency. Download-at-start
  makes the first start depend on network and an outside service. A shared volume is the right choice once
  several images use the same weights.
- **Download only what is loaded.** Both repos also contain `pytorch_model.bin`, and the NLI repo an `onnx/`
  directory of 1.1 GB + 0.34 GB `[card]`. An unfiltered snapshot of the NLI repo is about 2.6 GB.
- **Corpus, registry, embedding cache**: seed copies in the image, named volumes on top (Docker initialises an
  empty named volume from the image path). An image upgrade does not refresh a populated volume — refresh through
  ingest or remove the volume.
- **Runtime DB**: volume `data/runtime`. SQLite is fine with one replica.
- **Readiness**: `GET /api/health` answers only after the startup hook loaded index and NLI. Cold start about
  10 s with a warm page cache `[M-team: COSTS.md]`; allow 30–90 s in a fresh container `[est]`, start period 120 s.
- **Cold start trap**: with a missing or mismatching embedding cache the service embeds 21,560 chunks before it
  answers — tens of minutes on a laptop CPU (the team measured ~20 min for half that size). The cache must be in
  the image.
- **Threads**: set `OMP_NUM_THREADS` to the CPU limit. `nli.py:42` takes torch's default, which follows the host
  core count rather than the container quota.

### 4.3 Configuration and secrets

- Everything is already `PRAWDOWID_*` environment variables (`config.py`), which suits containers.
- `.env` via compose `env_file`, never copied into the image. It must be in `.dockerignore`.
- Tokens have working demo defaults (`config.py:61-62`). Keep them for `docker compose up` on a laptop; require
  explicit values in any public deployment.
- `web_dir` is fixed to `ROOT/web` (`config.py:21`); fine while the API serves the UI.

Notes on the minimal path:
- The `tunnel` profile needs `FORWARDED_ALLOW_IPS=*`, otherwise all tunnel users share one rate-limit bucket.
- With `PRAWDOWID_SCHEDULER=0` the index does not reload by itself (the watcher lives in the scheduler loop);
  use `POST /api/admin/reload` after a refresh.
- `pyarrow` (one ingest script) is left out to save about 100 MB `[est]`; that source will report an error.
- `torch==2.15.0` matches the local venv `[local]`. Pin the remaining packages from `uv pip freeze` — the
  requirements file has no versions, so today's build and next week's can differ.
- Both tiers run in the `app` container: `/api/quick` and `/api/check/async`. They share the CPU, so tier-1
  latency degrades while a tier-2 job runs. A second container from the same image would fix that at the price
  of another 2–2.5 GB of RAM `[est]`.

### 4.8 How the two tiers map

| | Minimal | Target |
|---|---|---|
| Tier 1 | `app`: `POST /api/quick` (alias `/api/v1/tag`), same process | `tagger` service, embedder only in the hot path, replicated, results cached in Redis |
| Tier 2 | `app`: `POST /api/check/async` + `GET /api/jobs/{id}`, 2 threads | `verifier` workers consuming the queue, one job per replica |
| Isolation | none — shared CPU | separate CPU limits; tier 1 cannot be starved by tier 2 |
| In-browser tier 1 (option C) | — | removes most `tagger` traffic; the service stays for clients without the model |

### 4.9 What I would ship for the hackathon

The minimal path: one image with baked models, one compose file, one uvicorn worker, SQLite on a volume,
scheduler off by default. It works with today's code, meets "runnable by the jury from instructions", and the
target topology can be shown as one slide with the code-change list. Splitting services before the deadline
buys no evaluation points and risks the end-to-end path, which is a hard requirement.

## 5. Decisions that are genuinely open

| # | Decision | My recommendation | Why |
|---|---|---|---|
| 1 | Run tier 2 automatically on passively viewed content, or only on click | Automatic for ≤ 3 items per page, local corpus only, no moderator case, text not stored; behind the existing consent | Gives the "upgrade to a sourced result" effect at bounded cost. Click-only is the defensible alternative if privacy review time is short. |
| 2 | Overlay or badge as the default for a match | Badge | An automated similarity match should not hide content by default; the ≥ 0.88 shortcut makes false overlays possible. Counter-argument: the overlay is the more striking demo. |
| 3 | Show "Potwierdzone" and "Brak dowodów" automatically | No; only false/misleading/conflict | Marking some items confirmed implies the unmarked ones are doubtful or fine, depending on the reader. |
| 4 | Tier 1 on the server or in the browser | Server now, browser model for the pilot | Browser is better for privacy and scale; it costs an export, a 118 MB download and MV3 plumbing. |
| 5 | Add a reranker or LLM to tier 2 before the deadline | No. Do the data fix (unmapped verdicts), more keys per fact-check, extraction cap | The measured misses are matching and data problems; a new model needs calibration time that is not there. |
| 6 | Bake models into the image or mount a volume | Bake | Reproducible offline start for the jury; costs 0.8 GB of image. |
| 7 | SQLite or Postgres now | SQLite | One replica. Postgres belongs with the split. |
| 8 | Scheduler on or off in the shipped container | Off by default, one-shot `ingest` profile | No surprise load or failing legacy scripts during a demo; "automatic updates" can still be shown by switching it on. |
| 9 | Google Fact Check API in the default configuration | Off unless a key is set (as now); never in automatic mode | Non-EEA processing of claim text must be a visible, deliberate choice. |
| 10 | Keep the ≥ 0.88 "same claim without NLI support" shortcut | Require entailment ≥ 0.5 or no equally close true-rated claim | Trades a little recall for protection against the worst error type. The team may prefer recall. |
